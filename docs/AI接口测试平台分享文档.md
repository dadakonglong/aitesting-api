# 基于大模型的自动化接口测试平台 — 公司内部分享

> 本文档面向内部 AI 分享：如何用大模型、向量检索、知识图谱等能力，做成一个「能理解需求、自动生成用例、自动执行并自愈」的接口测试平台，以及分别解决了哪些痛点。

---

## 一、平台定位与目标

### 1.1 我们做了什么

一个 **AI 驱动的接口测试平台**，核心能力包括：

- **自然语言驱动**：用一句话描述业务场景（如「测试点单流程」），系统自动理解意图、挑选接口、编排步骤、补全参数依赖并执行。
- **单接口深度测试**：针对单个 API，从需求理解 → 测试计划 → 用例生成 → 执行 → 结果分析，全流程由多阶段 Agent + 大模型完成。
- **执行后自愈**：执行失败时，AI 分析失败原因并支持「一键修复」——自动修改用例步骤（如鉴权、字段映射），减少人工改用例成本。

### 1.2 目标用户与价值

| 角色         | 痛点                           | 平台提供的价值                         |
|--------------|--------------------------------|----------------------------------------|
| 测试工程师   | 接口多、场景杂，手工写用例慢   | 自然语言生成场景用例，自动编排与执行   |
| 开发/测试    | 单接口要覆盖正向/边界/安全等   | 一键生成计划与用例，自动执行并出报告   |
| 团队          | 用例失败后排查、改步骤费时     | 失败分析 + 一键应用修复，用例可自愈   |

## 二、整体架构：AI 在哪里起作用

```
┌─────────────────────────────────────────────────────────────────────────┐
│                            前端 (Next.js)                                 │
│  测试中心 / 测试场景 / 接口测试计划 / API 管理 / 项目与环境                 │
└───────────────────────────────────┬─────────────────────────────────────┘
                                    │ HTTP
                                    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                    AI 处理服务 (main_sqlite.py)                           │
│  • 场景 NLU、场景用例生成、万能执行引擎、Healer、单接口流水线入口            │
│  • 统一调度：大模型对话、向量检索、知识图谱                                 │
└───────┬─────────────────────┬─────────────────────┬─────────────────────┘
        │                     │                     │
        ▼                     ▼                     ▼
┌───────────────┐   ┌─────────────────┐   ┌─────────────────────────────┐
│  大模型 (LLM)  │   │  向量服务       │   │  知识图谱 (NetworkX)          │
│  OpenAI/      │   │  Qdrant +       │   │  节点=API，边=依赖关系       │
│  DeepSeek 等  │   │  Embedding      │   │  执行后自动学习，生成/执行时  │
│  对话+Embedding│   │  语义检索 API   │   │  用于补全与依赖解析           │
└───────────────┘   └─────────────────┘   └─────────────────────────────┘
```

- **大模型**：意图理解、步骤编排、测试计划、代码/用例生成、失败分析、修复建议等，贯穿「生成」与「分析」。
- **向量服务**：把接口描述向量化存进 Qdrant，按「场景意图」做语义检索，解决「接口太多、关键词对不上」的痛点。
- **知识图谱**：记录「谁依赖谁、字段怎么映射」，在生成时提供上下文、执行前补全映射、单接口执行前自动插登录等前置依赖。

## 三、大模型在平台中的具体用法

### 3.1 场景侧：从自然语言到可执行用例

| 阶段     | 输入               | 大模型作用           | 输出 / 下游           |
|----------|--------------------|----------------------|------------------------|
| 场景理解 | 用户一句话描述     | 结构化意图（intent、actions 等） | 场景元数据、后续检索 query |
| API 检索 | 意图 + 项目内 API  | 不直接参与           | 由**向量检索**或关键词排序得到候选 API |
| 步骤编排 | 意图 + 候选 API + 知识图谱依赖 | **按规则生成 JSON 步骤**（顺序、param_mappings、鉴权等） | steps（含 from_step/to_field 等） |
| 执行     | steps + base_url   | 不参与               | 万能执行引擎跑 HTTP，写执行记录 |
| 执行后学习 | steps + 执行结果  | 不参与               | **知识图谱**按 param_mappings 学习边 |

编排时的 Prompt 会明确要求：识别依赖、登录 Token 映射到后续 Authorization、禁止自引用、若提供「知识图谱：常见依赖关系」则优先参考等，从而把大模型与图谱结合起来。

### 3.2 单接口侧：五阶段流水线（Agent 串联）

单接口测试采用 **多阶段 Agent + 大模型** 的流水线（见 `single_api_pipeline`）：

| 阶段       | 名称         | 大模型 / 其他能力 | 输入 → 输出 |
|------------|--------------|-------------------|-------------|
| 1          | 需求理解     | RAG 检索 + 大模型 | 用户描述 → 结构化（entities、relationships、chunks、target_api_indices） |
| 2          | 测试计划     | Planner Agent     | API 信息 → Markdown 测试计划（目标、用例列表、数据与环境要求） |
| 3          | 代码/用例生成 | Generator Agent  | 计划 + 用例列表 → Playwright/pytest 风格用例或直接 steps |
| 4          | 执行         | 执行引擎（可先依赖解析） | steps → HTTP 请求、结果收集 |
| 5          | 结果分析     | Analyzer Agent    | 执行结果 → 分析报告、根因、改进建议 |

依赖解析（阶段 4 前）**优先查知识图谱**：若该接口在图谱中有高置信度前置依赖（如登录），则直接插入前置步骤，不再走 RAG+AI，减少延迟与幻觉。

### 3.3 失败自愈（Healer）

- **分析**：根据某次执行的 `results`（含请求/响应/状态码），大模型分析失败类型、根因、修复建议、`patch_hint`。
- **应用修复**：根据分析结果，大模型生成对当前用例 steps 的修改（如补全 Authorization 映射、修正字段路径），写回 DB，并记录到 `healing_records`。

这样就把「执行失败」和「用例迭代」闭环到「一键修复」，减少人工改步骤的成本。

## 四、向量检索：解决「接口太多、搜不准」的痛点

### 4.1 痛点

- 项目里可能有几十、上百个接口，按 path/关键词很难和「点单流程」「开台关台」等业务意图对上。
- 若把所有 API 都塞进 Prompt，token 爆炸且模型容易选错。

### 4.2 方案：Qdrant + Embedding 语义检索

- **存储**：接口导入/同步时，用 **OpenAI text-embedding-3-small** 对「path + method + summary + description」做向量化，写入 **Qdrant** 的 `api_knowledge` 集合，按 `project_id` 过滤。
- **使用**：场景生成用例时，用「自然语言输入 + 意图 + actions」拼成 query，做**语义检索**，取 top-K（如 50）接口再交给大模型编排。
- **降级**：若未配置 Qdrant 或 Embedding，则退化为「关键词 + 意图排序」选 API，保证无向量时平台仍可用。

### 4.3 效果

- 用户说「测试点单流程」，能召回与点单、下单、订单相关的接口，而不是仅匹配到 path 里带「order」的少数几个。
- 检索阶段就压缩候选集，编排阶段只对高相关 API 做步骤生成，既省 token 又提高编排质量。

## 五、知识图谱：解决「谁先谁后、谁依赖谁」的痛点

### 5.1 痛点

- 场景用例需要**正确顺序**（如先登录再下单）和**参数传递**（如 Token → Authorization）。
- 单接口测试时，若测的是「需要登录的接口」，也要先插登录步骤并配置好映射。
- 纯靠大模型「猜」顺序和映射，容易漏、错，且每次重新猜成本高。

### 5.2 方案：轻量级知识图谱（NetworkX）

- **结构**：有向图，节点 = API（`project_id:METHOD:path`），边 = 依赖关系，边上带 `field_mapping`、`count`、`success_count`（用于置信度）。
- **写入**：  
  - 接口**导入**时：只建节点，不建边。  
  - **场景用例执行后**：从 steps 的 `param_mappings` 抽「from_step → to_step」对应 API，写边；若本次执行整体成功则提高该边 `success_count`，失败则降低，便于后续按置信度过滤。
- **读取**：  
  - **生成场景用例时**：按候选 API 取「高置信度依赖边」，以「知识图谱：常见依赖关系」形式拼进 Prompt，让大模型优先参考顺序与字段映射。  
  - **场景执行前**：对 steps 做**映射补全**——对每一步查其前置节点，若前置已在当前步骤里则自动补 `param_mappings`（不覆盖已有）。  
  - **单接口执行前**：依赖解析时**先查图谱**，若有高置信度前置则直接构建前置链并插入，不再走 RAG+AI。

### 5.3 效果

- 顺序与映射会随着「真实执行结果」越用越准，失败多的边置信度下降后自动淡出。
- 新场景生成时可直接复用历史沉淀的依赖关系，减少模型乱猜；执行前补全能避免「漏配 Token」等常见问题。

## 六、场景用例端到端：从说到跑再到修

### 6.1 流程简述

1. **创建场景**：用户输入一句话（如「测试点单流程的完整性和正确性」）→ 大模型 NLU → 存场景（name、intent、actions 等）。
2. **生成用例**：  
   - 用意图 + 描述做**向量语义检索**（或关键词排序）得到候选 API；  
   - 从**知识图谱**取相关依赖边，拼进 Prompt；  
   - 大模型输出 steps（含 param_mappings）；  
   - 可选：用 API 的 headers 等做步骤增强后落库。
3. **执行**：  
   - 若有知识图谱，先对 steps 做**映射补全**；  
   - 万能执行引擎按 steps 发 HTTP，按顺序传递上下文（如 Token）；  
   - 结果写入 `executions`；若为场景用例且启用图谱，则**学习依赖边**（成功/失败影响边的 success_count）。
4. **失败时**：前端展示失败信息，用户可点「一键修复」→ 后端用 Healer 根据该次 `execution_id` 分析并修改对应 `test_case` 的 steps。

### 6.2 痛点与对应能力

| 痛点                     | 用的能力           | 说明 |
|--------------------------|--------------------|------|
| 不知道选哪些接口         | 向量语义检索       | 意图与描述 → 高相关 API 列表 |
| 顺序、依赖容易错/漏     | 知识图谱 + Prompt  | 图谱提供常见依赖，模型按规则生成并补全 |
| 执行时漏配 Token 等     | 执行前图谱补全     | 按前置节点自动补 param_mappings |
| 失败后改用例费时       | Healer 分析+应用   | 一次执行失败也可落库，返回 execution_id 供修复 |

## 七、单接口用例端到端：五阶段 + 依赖解析

### 7.1 流程简述

1. **需求理解**：用户描述（如「测登录接口」）→ 向量/关键词 RAG 检索项目内 API → 大模型结构化（target_api_indices、entities、chunks 等）。
2. **测试计划**：Planner 根据 API 信息生成 Markdown 计划（范围、用例类型、数据要求等）。
3. **用例生成**：Generator 根据计划（及已有 plan 中的 cases）生成可执行步骤或 Playwright 风格用例。
4. **依赖解析**（若执行的是需鉴权的接口）：  
   - **先查知识图谱**：该 API 的前置依赖；若有则直接插入登录等前置步骤；  
   - 若无，再走 RAG + 大模型分析依赖链。
5. **执行**：按步骤发 HTTP，收集结果。
6. **结果分析**：Analyzer 大模型生成报告（统计、失败分析、根因、建议）。

### 7.2 痛点与对应能力

| 痛点                         | 用的能力           | 说明 |
|------------------------------|--------------------|------|
| 不知道测哪些点、怎么写用例   | 多阶段 Agent       | 需求理解 → 计划 → 生成，每步由专门 Prompt 完成 |
| 单接口需要先登录/鉴权        | 知识图谱优先的依赖解析 | 图谱有则直接用，减少 RAG+AI 延迟与错误 |
| 结果看不懂、不知道咋改       | Analyzer + Healer  | 报告 + 可选的一键应用修复 |

## 八、技术栈与可复用的 AI 实践

### 8.1 技术栈

| 层次     | 技术 |
|----------|------|
| 前端     | Next.js |
| 后端/AI  | Python, FastAPI, SQLite |
| 大模型   | OpenAI / DeepSeek 等（对话 + Embedding） |
| 向量库   | Qdrant（本地或云） |
| 知识图谱 | NetworkX，持久化 pkl |

### 8.2 可复用的实践

- **多阶段 Agent 流水线**：把「需求理解 → 计划 → 生成 → 执行 → 分析」拆成多步，每步专用 Prompt 和少量结构化 I/O，便于迭代和排错。
- **RAG + 图谱分工**：  
  - RAG（向量/关键词）解决「从海量候选中召回相关项」；  
  - 图谱解决「结构化关系（顺序、依赖、映射）」；  
  - 大模型做「理解、生成、分析」，三者结合而不是单靠模型「硬想」。
- **执行即学习**：场景执行结果反哺知识图谱，成功/失败反馈到边的置信度，形成「越用越准」的闭环。
- **降级策略**：向量未配置时退化为关键词；图谱未启用时跳过补全与图谱学习，保证主流程仍可用。

## 九、总结：痛点与方案对照表

| 痛点 | 方案 | 涉及能力 |
|------|------|----------|
| 接口太多，和业务意图对不上 | 按意图做语义检索，只把相关 API 给模型 | 向量 + Embedding |
| 场景顺序、参数依赖容易错/漏 | 图谱记录依赖与映射，生成时参考、执行前补全 | 知识图谱 + 大模型编排 |
| 单接口不知道测什么、怎么写 | 多阶段 Agent：需求理解→计划→生成 | 大模型 + RAG |
| 单接口需要登录等前置步骤 | 执行前依赖解析，优先用图谱前置链 | 知识图谱 + 执行引擎 |
| 用例失败后排查、改步骤费时 | 失败分析 + 一键应用修复 | 大模型 Healer + execution_id 闭环 |
| 依赖关系不想全靠模型猜 | 执行结果反哺图谱，置信度过滤 | 知识图谱自动学习 |

## 十、分享时可强调的几句话

1. **「用 AI 做接口测试」不是让模型替人点按钮，而是把「理解需求、选接口、编排步骤、补依赖、执行、分析、修用例」串成一条流水线，大模型、向量、图谱各管一段。**
2. **向量解决「找得准」——从成百个接口里按语义召回；图谱解决「排得对、传得对」——谁先谁后、谁给谁传什么字段。**
3. **执行结果反哺知识图谱，形成「用得越多，依赖关系越准」的正向循环，这是和纯 Prompt 方案的重要区别。**
4. **失败自愈（Healer）+ 失败也落执行记录并返回 execution_id，让「执行失败」也能成为「修复用例」的输入，而不是死胡同。**
